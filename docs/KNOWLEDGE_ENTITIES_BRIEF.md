# 知识实体体系 —— 给领域专家的背景说明

> 面向对象：即将参与知识实体编辑的**生物化学 / 分子生物学博士**
> 目的：在你开始判断"这条链接对不对"之前，先知道**这套东西为什么存在、哪部分可信、你的一句话会改变什么**
> 数据均为 **2026-10-29 生产库实测**，不是设计稿

---

## 1. 为什么要有这套东西

如果这个网站只是一张「产品名 – CAS – 价格」的表，那它和任何一个试剂电商没有区别，客户只能靠**自己已有的知识**来找东西。

知识实体体系要做的是反过来：**让网站能回答"我想做 X，该用什么"**，而不只是"你想买什么，我有没有"。

具体是三件事：

1. **把科研认知链固化下来**：研究目标 → 应用场景 → 方法 → 实验方案 → 具体试剂。这条链在研究员脑子里和论文里是隐性的，我们把它变成可检索、可追溯的数据。
2. **让产品挂在知识上，而不是孤立存在**：一个产品不只是 SKU，它是"某个方法里的一种试剂""被某篇文献支持""和另一个产品兼容/互斥"。
3. **一个数据底座喂所有出口**：首页、产品详情、搜索、知识图谱，都读同一套数据，不会出现"页面 A 说有 3 个方法、页面 B 说有 5 个"。

一句话：**知识实体是平台的"大脑"，产品是"身体"。**

## 2. 七个实体分别是什么

| 实体 | 领域含义 | 举例 | 生产数量 |
|---|---|---|---|
| **ResearchGoal** 研究目标 | 顶层科研意图，回答"为什么做" | RNA Labeling and Detection | **11,045** |
| **Application** 应用场景 | 按用途把方法归类，回答"在什么场景下用" | Nucleic Acid Labeling | **28,570** |
| **Method** 方法 | 一类工作流 / 技术路线，回答"用什么办法" | Click Chemistry Labeling | **47,935** |
| **Protocol** 实验方案 | 具体可操作的步骤集（通常对应一篇论文/一份说明书） | 某篇 2019 年文章的标记方案 | **14,128** |
| **ProtocolStep** 步骤 | 协议里的有序原子操作（含时长、注意事项） | "1. 将 dATP 溶于水，冰上放置 10 min" | **380,953** |
| **Reference** 文献 | 规范化引用（DOI/PMID） | 某篇 Nature Methods 文章 | **437** |
| **ReagentClass** 试剂功能类 | 按**功能角色**给试剂分类（不是按化学结构） | Azide-modified nucleotide | **37** |
| **Product** 产品 | 链末端的可售物（商业实体，不是知识实体） | SC8001 5-Ethynyl-dUTP | **125** |

> 数量差了两个数量级不是笔误：**Method 有近 5 万条，而产品只有 125 个**。原因见第 5 节。

## 3. 它们之间怎么连

### 3.1 纵向主链（父子）

```
ResearchGoal ──► Application ──► Method
  研究目标          应用场景        方法
                                   │
                                   │  ⚠️ 多对多（不是一对多）
                                   ▼
                                Protocol ──► ProtocolStep
                                实验方案        步骤
```

**这里有一个容易误解的点**：Method 和 Protocol 是**多对多**关系（桥表 15,241 条）。
一份协议可以同时服务多个方法（比如一个通用标记方案既属于"点击化学标记"也属于"炔基修饰检测"），
一个方法下也会有几十上百份协议。

### 3.2 横向桥接（产品接入知识链）

产品通过**带语义的桥**接进知识链，桥不是"连上就行"，每条都带判断：

| 桥 | 连接 | 携带的判断 |
|---|---|---|
| `ProductMethod` | 产品 ↔ 方法 | 角色（reagent / buffer / control / label…）+ 证据等级（low / medium / high / curated） |
| `ProductProtocol` | 产品 ↔ 协议 | 这个产品能不能用于这份协议 —— **23,431 条，是产品页面"相关协议"的来源** |
| `MethodProtocol` | 方法 ↔ 协议 | 是否 featured（代表方案） |
| `ProductReference` | 产品 ↔ 文献 | 引用角色（primary / supporting / validation / background） |
| `ProductMethodRelation` | 产品 ↔ 方法 | **两种边**：`derived_relevance`（机器按试剂类推导）vs `verified_applicability`（人工验证过） |

### 3.3 为什么要有"两种边"

这是整套设计里最重要的一条原则：

> **机器推出来的关系**和**人确认过的关系**，必须分开存，不能混在一个字段里。

- `derived_relevance`：因为"这个产品属于 Azide-modified nucleotide 类，该类被用于 Click Chemistry Labeling"，所以推断它和这个方法相关。**可能对，也可能错。**
- `verified_applicability`：有博士看过、确认"这个产品确实能用于这个方法"。**这才敢给客户看**。

**当前生产状态：这两类边一共只有 159 条，且 159 条全部是机器推导，人工验证的一条都没有。** 这是需要你参与的核心原因之一。

## 4. 客户在网站上看到什么

| 位置 | 看到的内容 | 数据来源 |
|---|---|---|
| **产品详情页 → Verified Applicability** | 这个产品被验证过能用于哪些方法 | `verified_applicability` 边 + 试剂类推导 |
| **产品详情页 → Protocols** | 这个产品相关的实验方案（目前只显示前 20 条，共可关联数百条） | `ProductProtocol` |
| **产品详情页 → References** | 支持这个产品的文献 | `ProductReference` |
| **产品详情页 → Related Products** | 替代品 / 补充品 | `ProductProduct` |
| **首页 → Knowledge Graph** | 研究目标 → 应用 → 方法的可视化 | 纵向链 |
| **搜索** | 按产品名 / CAS / 货号 / 方法名 / 协议标题 | 全文检索索引 |
| **知识索引页** | `/research-goals`、`/applications`、`/methods`、`/protocols` | 对应实体列表 |

**换句话说：你在后台改的一条关系，会直接出现在客户看到的产品页上。** 所以"这条链接对不对"不是整理数据，是在对客户做承诺。

## 5. 数据是怎么来的（这一节决定你怎么看待现有数据）

### 5.1 来源构成

| 来源 | 标记 | 现状 |
|---|---|---|
| **AI 从协议全文抽取** | `origin = ai_extracted` | Method：**47,844 / 47,935（99.8%）** |
| **人工策展** | `origin = human_curated` | 极少 |
| **存量导入** | `origin = imported` | Method 91 条 |

Method 的**状态分布**更能说明问题：

```
draft   47,834   ← AI 抽取后躺在草稿区，从未有人看过
active      93   ← 真正在前台展示的
archived     8
```

⇒ **你在网站上看到的 93 个方法，是从 4.8 万个候选里挑出来的。剩下 47,834 个是"机器觉得它们可能是方法"。**

### 5.2 抽取管线怎么工作的

1. 把 14,128 份协议全文（来自厂商说明书、论文方法部分）喂给大模型
2. 让它抽出：这份协议属于什么方法、什么应用、什么研究目标
3. 写入 Method / Application / ResearchGoal，`origin = ai_extracted`，**状态全部为 draft**
4. 人工（或规则）审核后，个别升为 `active`

**关键：AI 抽取的结果默认不进前台。** 所以"47,834 个 draft" 不是脏数据，是**待审队列**。

### 5.3 产品侧的数据

| 数据 | 来源 | 可信度 |
|---|---|---|
| 产品的化学属性（CAS/SMILES/分子式/结构式） | 厂商资料 + PubChem 校正 | 较高 |
| 产品 ↔ 协议（23,431 条） | 由厂商说明书文件名/内容批量关联 | **中等，可能有误关联** |
| 产品 ↔ 方法（22 条） | 人工 | 高，但**极少** |
| 产品 ↔ 文献（467 条） | Bioz / EuropePMC 抓取 | 中等 |

## 6. 现在的问题（你大概率会遇到的）

按"对客户的影响"排序：

**① 人工验证的关系几乎为零**
`ProductMethodRelation` 的 159 条全是机器推导，`verified_applicability` 一条都没有。
⇒ 产品页上"这个产品能用于这个方法"目前**没有任何一条是博士确认过的**。

**② 产品挂的协议可能不准**
23,431 条 `ProductProtocol` 里，同一产品平均挂 187 份协议。这个数量本身就可疑——一个试剂不太可能真的出现在 187 份实验方案里。很可能是**按厂商说明书批量关联**时把"该说明书提到过这个试剂"当成了"这个试剂适用于这份协议"。

> 实测例子：某产品的详情页一次返回 233 条协议，等于把整份清单堆给客户。

**③ 方法链的"活性"极低**
47,935 个 Method 只有 93 个 active。虽然不影响前台，但意味着**知识图谱的覆盖率其实很窄**。

**④ 文献支撑严重不足**
437 条 Reference 对 125 个产品、4.8 万个方法。绝大多数方法**没有任何文献支撑**。

**⑤ 试剂功能类只有 37 个**
`ReagentClass` 是"机器推导产品↔方法"的依据。37 类撑 4.8 万个方法，粒度可能过粗。

**⑥ 上游链可能挂错**
Application 挂在 ResearchGoal 下、Method 挂在 Application 下，这些父子关系大多是 AI 一次抽出来的，没有独立验证过。**一条父级挂错，整棵子树都错位。**

## 7. 你具体要做什么

不是录入数据，是**做判断**。典型动作有三种：

| 动作 | 你做的是 | 影响 |
|---|---|---|
| **激活方法**（draft → active） | 看这个方法名、所属应用、"为什么它算一个方法" | 它会出现在方法索引页和搜索里 |
| **确认适用性**（写 `verified_applicability`） | 判断"这个产品是否真能用于这个方法"，附证据（文献 DOI / 实验结果） | 会出现在产品页的 Verified Applicability，客户据此下单 |
| **修正关系**（删掉错的 `ProductProtocol`） | 判断"这份协议真的用到这个试剂吗" | 产品页的协议列表会缩短，但变准 |

**判断标准建议（供讨论）**：

- **能用于**：该方案里明确使用了这个试剂，或使用了化学等价的试剂（需说明等价性依据）
- **不能用于**：只是同一类试剂但官能团不同、浓度/形态不兼容、方案里只在"可选步骤"提及
- **不确定**：留空，不要猜。**空的代价远小于错**

---

## 8. 两条希望你遵守的原则

1. **宁缺勿错。** 现在的问题不是"数据太少"，而是"看起来很多但没验证"。一条错误的关系会让客户买到用不上的试剂，这比"没写"伤害大得多。
2. **每条判断留证据。** 写清楚依据（哪篇文献的第几段、厂家的哪份说明书），方便下一个人复核，也方便将来解释给客户。
