# 「全局测试」的正式定义（2026-10-21 定稿）

> 这份文档是团队口径。它与 `COVERAGE_STATUS.md`（现状台账）分工不同：
> **本文定义"什么算测到位"，`COVERAGE_STATUS.md` 记录"现在测到哪"**。

## 0. 一句话定义

> **全局测试 = 系统中的每一类失效模式，都有明确的归属状态：**
> **要么被自动化验证覆盖，要么被书面记录为「已知不测 + 为什么 + 人工怎么兜」。**
> **没有第三种状态——「没人知道这里没测」是不可接受的。**

判据是可检验的：拿失效模式清单逐条问"它的归属是什么"。**答不出来的那一行就是盲区。**

## 1. 这个定义要拆掉的三个误解

| 误解 | 为什么错 |
|---|---|
| 全局 = 全部测到 | 组合空间无限，不可达；追求它只会得到"看起来很多其实没重点"的用例堆 |
| 全局 = 覆盖率高 | 覆盖率只回答"哪些代码被执行过"，不回答"哪些失效模式没人管"。100% 行覆盖的代码照样能在生产上出事 |
| 全局 = 所有测试类型的合集 | 按**测试手段**分类，必然漏掉"还没有对应手段"的风险。必须按**风险来源**分类 |

## 2. 三个正交轴 + 两个横切面

### 轴 1 · 功能维度（做什么会错）
用户交互 / 权限与数据隔离 / 状态与流转 / 数据契约 / 响应式 / 视觉 / 可访问 / 浏览器兼容。

> 这就是原来的「7 维」，保留。它是最成熟的一维。

### 轴 2 · 状态与条件（在什么条件下会错）
| 条件 | 必须回答的问题 |
|---|---|
| 数据量级 | 当前规模撑得住，10 倍 / 100 倍呢？ |
| 数据状态 | 空 / 单条 / 大量 / 极端值 / 脏数据 / 半写状态 |
| 时间边界 | 跨日、跨月结、跨年、时区、夏令时 |
| 生命周期 | 创建 → 使用 → 修改 → 软删 → 恢复 → 彻底删除（级联一致性） |
| 依赖失效 | 外网挂 / DB 挂 / 缓存挂 / 磁盘满 / 内存不足 ⇒ 是降级还是雪崩 |
| 身份 | 匿名 / 新注册未验证 / 普通 / 机构管理员 / 采购 / 超管 |

### 轴 3 · 验证强度（测得多深）
- **浅**：断言 HTTP 200 —— 几乎不证明任何事
- **中**：断言字段值
- **深**：断言**业务不变量**（库存守恒）+ **副作用**（审计日志、邮件入队）+ **反向**（不该发生的确实没发生）

> 强度必须能被校准。唯一可靠的校准手段是**变异验证**：
> 把代码改坏，看测试会不会红。不红的测试，无论有多少条，强度都是 0。

### 横切面 A · 环境一致性
配置项差异（dev / CI / prod）、依赖版本、容器挂载语义、时区与本地化、网络可达性。

> **为什么它是横切面而不是普通一维**：它不针对某个功能，而是**让所有功能在不同环境下表现一致**。
> 本项目已为此付过代价：`ALLOWED_HOSTS` 导致全部端点 400、`DEBUG` 默认 True、
> 单文件 bind mount 不跟 inode、sqlite 让并发测试假红 —— **这些坑一个都不在旧 7×7 框架里。**

### 横切面 B · 可观测性
关键路径是否留下足以定位问题的日志？错误是否可追溯？告警是否存在且有效？

> 测试和运维的交界。「测不到」的失效模式，最终要靠可观测性兜住 —— 如果连日志都没有，
> 那这条失效模式就是**真盲区**，不属于"已知不测"。

## 3. 广度与深度不可互相替代

- **广度** = 有多少类风险**有归属**（不是"被测"，是"被认领"）
- **深度** = 每类风险的验证**能不能区分真假**

| 组合 | 后果 |
|---|---|
| 广度大 + 深度浅 | **虚假安全感**（本项目曾经的样子：263 格全绿，但 A 维 44 个 ✓ 只有 10/35 真通过） |
| 深度大 + 广度小 | **精致的局部**（库存并发测得很深，但 14 处 `select_for_update` 从未碰过） |

⇒ **任何"全局测试完成度"的数字，必须同时报广度和深度，单独报一个是误导。**

## 4. 归属状态：只有三种，不许有第四种

| 状态 | 含义 | 载体要求 |
|---|---|---|
| **A 自动化** | 有闸门/测试能拦住退化 | 必须在 CI 或 pre-commit 里能跑 |
| **B 已知不测** | 明确不测，但写清*为什么*与*人工怎么兜* | 必须写明兜底动作与责任人角色 |
| **C 不适用** | 该类风险在本系统不存在 | 必须写理由（例如"无支付网关 ⇒ 无 PCI 范围"） |

**第四种「没人知道」= 盲区 = 必须消除。**

> ⚠️ 状态 A 的常见伪实现：「写了测试但从没跑过」「跑了但断言恒真」「只在本地跑」。
> 判定 A 的唯一标准是：**把对应代码改坏，闸门会红**（变异验证）。做不到就不是 A。

### 4.1 B 类的兜底不得是「无」（2026-10-21 补充，血的教训）

这条规则是定义**自己漏掉的**：最初只要求"写明兜底"，没要求兜底必须是**真的**。
结果 `FAILURE_MODES.md` 第一版就出现了这样的行：

| 条目 | 兜底怎么写的 |
|---|---|
| 死锁 | 「**无**；属已知风险」 |
| DB 不可用 | 「**无**」 |
| 磁盘满 | 「监控（**当前无告警**）」= 没有 |
| 关键路径无日志 | 「报障时**靠复现**」 |

**「兜底 = 无」的 B 类，实质就是盲区，只是贴了个 B 的标签自我安慰** ——
被本定义明确排除的第四种状态（"没人知道"），从后门溜回来了。

⇒ **硬规则：B 类的兜底必须是「一个能被执行的、有承担者的动作」。**

| 不合格（等于空白） | 合格（可执行 + 有承担者） |
|---|---|
| 无 | 改这些路径时跑 `run_pg_tests.py` 并人工确认锁点 |
| 属已知风险 | 新增日期逻辑必须写 `business_today()` 用例 |
| 靠复现 | PR 需人工检查前端枚举映射 |
| 监控（但没有告警） | 删除前跑 `capability_guard --check` |
| 以后再说 | — |

**不合格的条目必须降级为「空白」**，而不是留在 B 类里充数。
空白是诚实的；假的 B 是有害的 —— 它会让"空白 = 0"这个数字失去意义。

## 5. 与旧框架的关系

| 旧框架 | 在新定义中的位置 |
|---|---|
| 7 维（交互/权限/状态/响应/视觉/可访问/浏览器） | 轴 1 的实现 |
| 7 层（L1 领域 / L2 API / L3 数据 / L4 并发 / L5 契约 / L6 E2E / L7 非功能） | 轴 3 的载体分类（"在哪一层验"） |
| 263 格覆盖矩阵 | 轴 1 × 页面 的格子计数 —— **只覆盖轴 1，不代表全局** |
| 第 5 节的"五条元规律" | 轴 3 的校准纪律（防假绿） |

⇒ 旧框架不是被推翻，而是**被降级为轴 1 的一个实现**。

## 6. 明确不做什么（边界）

- 不追求 100% 代码覆盖率（它不度量"失效模式是否有人管"）
- 不对每个端点都做全维度测试（组合爆炸，收益递减）
- 不测第三方库内部行为（只测"我们如何用它、它坏了我们怎么办"）
- 不为"不可能发生"的组合写用例（但要写进 C 类并给理由）

## 7. 怎么用这份定义

### 新增一条风险时（三条必答）
1. 它属于哪个轴/哪个面？
2. 归属状态是 A / B / C 哪一个？
3. 若是 A：**怎么证明它能红**？若是 B：**人工兜底动作是什么**？

### 每轮测试工作结束时
更新 `FAILURE_MODES.md` 的归属列 —— **不允许出现空白行**。

### 评估"完成度"时
不许只报一个百分比，必须给：
- 每种归属状态的条数（A / B / C / **空白**）
- 广度：空白行数（应为 0）
- 深度：至少抽样 N 条 A 类做变异验证，报告"能红"的比例

---

**附：这份定义的产生背景**

旧框架把"全局"等同于"7 维 × 7 层的覆盖率"。用本轮所有真实踩坑去对照，发现**一半以上的坑
不在框架任何格子里**（`ALLOWED_HOSTS` 400、`DEBUG` 默认 True、bind mount inode、
模型未生成迁移、sqlite 假红、两个 pytest 抢库、404 误判为 dev server 坏）。
这说明框架测的是"代码在正确环境下的正确性"，缺了"环境本身是否正确"整层。
本定义把环境与可观测性补为横切面，并引入"归属状态"作为可判定的完成判据。
