## 一、我们为什么要转型——从"卖货网站"到"科学知识平台"

### 1.1 转型前的状态

我们的起点是一个常规的试剂电商站点：产品列表、搜索、报价、下单。这类网站的竞争格局非常清晰——同质化严重、价格敏感、用户粘性低。客户来只是为了买到某样东西，买完就走。

在生物化学试剂这个细分领域，**试剂的价值远不止"可售物"这么简单**。一个 dATP（脱氧腺苷三磷酸）对于不同研究者意味着完全不同的东西：

- 做 RNA 标记的研究员关心的是 **"它在哪些应用场景中被使用过"**
- 做点击化学的研究员关心的是 **"它与哪些方法兼容、有无文献支撑"**
- 做 mRNA 合成的研究员关心的是 **"相关的实验协议是什么步骤、需要哪些配套试剂"**
- 采购人员关心的是 **"它交的 SDS 安全数据表是否符合实验室合规要求"**

传统电商的「名称-CAS-价格-下单」模型，**完全无法回答这些问题**。这就是我们转型的根本原因。

### 1.2 转成了什么

我们不做一个"能买东西的科学仓库"，而是做一个**"科学家能做科研、能买到试剂、且两者之间有可追溯关联的智能平台"**。

这个平台的核心设计理念可以用一句话概括：

```
研究目标 → 应用场景 → 科研方法 → 实验协议 → 产品 → SKU → 采购
```

这就是我们平台**不可改变的核心链路**。它回答的不是"你买什么"，而是**"你为什么需要它、它在你研究中扮演什么角色、它被科学共同体如何验证"**。

### 1.3 差异化价值

| 维度 | 传统试剂电商 | SciReAgent 知识图谱平台 |
|------|------------|----------------------|
| 产品呈现 | 名称 + CAS + 价格 | 名称 + CAS + **关联应用/方法/协议/文献** |
| 搜索 | 关键词匹配 | **按研究意图导航 + 知识图谱可视化** |
| 数据创建 | 手动填写 | **AI 一键预填（五数据源聚合）** |
| 合规文档 | 手动整理 | **COA/SDS 自动生成** |
| AI 可读性 | 无 | **结构化 JSON-LD + 机器可消费的知识图谱** |
| 科学可信度 | 供应商描述 | **文献引用 + 兼容性校验 + 证据等级** |

## 二、转型背后的完整设计体系

### 2.1 知识图谱——平台的"大脑"

如果产品只是货架，知识图谱就是让货架"长脑子"的系统。我们设计了**7 种知识实体**和**5 种语义桥接表**，共同构成完整的科学语义网络。

#### 7 种知识实体（分三大类）

**A. 知识实体**（描述"科研世界是什么、怎么做"）

| 实体 | 含义 | 关键字段 |
|------|------|----------|
| ResearchGoal（研究目标） | 顶层科研意图 | name, summary, priority |
| Application（应用场景） | 按用途分组方法 | research_goal(父级), summary |
| Method（科研方法） | 工作流家族 | application(父级), purpose, cost_band, timeline |
| Protocol（实验协议） | 版本化实验步骤 | method(父级), version, objective, materials, reagents |
| ProtocolStep（协议步骤） | 有序原子操作 | protocol(父级), step_no, title, body, duration_seconds |
| Reference（参考文献） | 规范化引用 | title, authors, journal, doi(唯一), pmid(唯一) |
| Compatibility（兼容性规则） | 试剂间兼容性定义 | scope, rule_type, expression_json |

**B. 商业实体**

| 实体 | 含义 |
|------|------|
| Product（产品） | 知识链的商业终点，含 CAS/SMILES/分子式/分子量/结构图等化学属性 |
| SKU（库存单元） | 产品的可售规格（包装大小、价格、库存状态） |

**C. 桥接表**（给关系赋予语义——这是知识图谱"有质量"的关键）

| 桥接表 | 连接 | 语义字段 |
|--------|------|----------|
| ProductMethod | Product ↔ Method | role（试剂/缓冲液/对照/酶/标记物/溶剂）+ evidence_level（低/中/高/人工审核） |
| MethodProtocol | Method ↔ Protocol | featured, status, display_order |
| ProductReference | Product ↔ Reference | citation_role（主引用/支持/验证/背景） |
| ProductCompatibility | Product ↔ Product + 兼容性规则 | verdict（兼容/不兼容/条件兼容/警告） |
| ProductProduct | Product ↔ Product | relation_type（替代/互补/备选/捆绑/相关） |

**关键设计理念**：同一个产品对同一个方法，可以同时是 `role=reagent, evidence_level=curated`（人工审核过的试剂用途）和 `role=control`（对照用途）。`unique_together = (product, method, role)` 允许多重语义共存。这不是简单的多对多链接表，而是带有丰富语义的**知识关系网络**。

#### 核心链路的架构示意

```
ResearchGoal ──▶ Application ──▶ Method ──▶ Protocol ──▶ ProtocolStep
                     │               │          │
                     │               │          └── 步骤 (试剂/设备/时长/警告)
                     │               │
                     │               └── 与 Product 通过桥接表关联
                     │                    (role=试剂/evidence_level=curated)
                     │
                     └── 与ProductMethod桥接
```

**产品不再是一个孤立的 SKU——它挂在知识图谱上的语义节点**。一个产品"是某个方法的试剂"、"被某篇文献支持"、"与某产品兼容"。反之，知识实体也通过产品获得商业落地。

### 2.2 数据底座——五数据源

产品的根本价值在于**数据质量**。研究员录入的产品属性，大部分可以从公开数据库自动获取。我们设计了**五个数据源**，各司其职、互不重叠：

| # | 数据源 | 类型 | 职能 | 独占价值 |
|---|--------|------|------|----------|
| 1 | **PubChem** | 外部 API | 化学结构权威源（CAS/SMILES/分子式/MW/Lipinski） | 唯一权威——化学属性不允许其他源直接写入 |
| 2 | **ChEMBL** | 外部 API | 化学结构 fallback（修饰核苷酸偶联物覆盖优于 PubChem） | 修饰核苷酸偶联物的补充覆盖（实测优于 PubChem） |
| 3 | **PubMed**（E-utilities） | 外部 API | 文献元数据 + 应用/方法关键词提取 | 17 种应用关键词模式 + 21 种方法关键词模式 |
| 4 | **BioProCorpus** | 本地语料库（~175MB） | 实验协议（试剂/设备/步骤富内容） | 14,675 条协议的试剂清单和步骤内容 |
| 5 | **jena 爬虫** | 本地数据集（策略 B） | systematic_name 锚点驱动 Bioz + 规格字段副产品 | systematic_name (96.6%覆盖) — 撬动跨厂家文献池的钥匙 |

**已评估并淘汰的候选源**：
- **ChEBI**：修饰核苷酸 0% 覆盖（已淘汰）
- **CAS Common Chemistry**：修饰核苷酸 0% 覆盖，功能被 PubChem 完全覆盖（已淘汰）

**关键发现（全部经实测/代码审计确认）**：
- jena 的 CAS 独占性 = 0%（299 个 CAS 全在 PubChem 已有），jena 的 CAS 仅作匹配锚点
- Bioz 必须用 systematic_name 查询，**CAS 不可用**（实测确认返回 "Missing"）
- 同一化学物质的文献跨 12 家供应商共享（如 dATP 一次返回 514 条文献 snippets）
- jena 现有数据已达标，无需二次爬虫（字段覆盖率审计结论）

### 2.3 AI AUTO MATCH——研究员生产力的核心杠杆

这是一个**一站式自动匹配与预填功能**。研究员在新建或编辑产品时，只要输入了产品的任一唯一性标识（产品名称 / CAS 号 / SMILES / InChI），点击一个按钮，系统在 5-30 秒内完成三件事：

```
┌─────────────────────────────────────────┐
│          AI AUTO MATCH 一键触发            │
│                                         │
│  ┌──────────┐  ┌──────────────┐  ┌─────────────┐ │
│  │ 化学属性   │  │ 知识链匹配    │  │ 实验协议推荐  │ │
│  │ 自动补全   │  │ 预勾选关联    │  │ 步骤内容返回  │ │
│  │          │  │              │  │             │ │
│  │ PubChem  │  │ PubMed 检索   │  │ BioProCorpus│ │
│  │ ChEMBL  │  │ 关键词提取    │  │ 本地 JSON   │ │
│  │ 降级策略  │  │ 反向匹配已有  │  │ 关键词检索   │ │
│  └──────────┘  └──────────────┘  └─────────────┘ │
│                                         │
│  返回预览 → 研究员审核 → "Apply All" 一键回填 │
└─────────────────────────────────────────┘
```

**一次 HTTP 调用，三类结果聚合返回**，研究员无需分别点击三次。返回结果以预览卡片展示，确认后点 `Apply All to Form` 一键回填。

**核心设计原则——研究员是最终权威**：
- 系统**只建议、不强制**，所有回填均为"只填空字段"
- 已由研究员填写的值**不会被覆盖**
- AI 推荐与落库严格解耦——所有 AI 服务只返回建议，绝不直接写库

**实测数据**（27 个产品的完整测试）：
- CAS 号搜索最可靠：精确匹配或 not found，无假阳性
- PubChem 名称搜索对修饰核苷酸覆盖差（如 Biotin-16-ddUTP 命中母核 dUTP），需分词降级
- ChEMBL fallback 对修饰核苷酸覆盖反而优于 PubChem
- 典型耗时：CAS 约 5 秒，精确产品名约 15 秒，需分词降级约 30 秒

### 2.4 COA / SDS——合规文档自动生成

COA（分析证书）和 SDS（安全数据表）是试剂行业采购的**硬性合规要求**。每批产品必须附带这两份文档。

**设计理念**：研究员完成产品信息录入 + AI AUTO MATCH 预填后，审核确认即可**一键生成 COA 和 SDS PDF**，无需人工排版或逐字录入安全数据。

#### 两份文档的数据依赖差异

| 文档 | 数据来源 | 外部 API 依赖 | 人工干预点 |
|------|----------|:---:|------|
| **COA** | 产品快照（create 时复制 Product）+ QC 实测值（人工录入） | 无 | QC 录入 + 审批签署 |
| **SDS** | PubChem（CAS → GHS 分类 + 属性 + 16 节数据）+ 类别通用安全模板兜底 | ⚠️ 有 | PubChem 不可用时选类别模板 + 审批 |

**关键设计**：COA 不依赖任何外部 API，数据完全可控；SDS 的 GHS 数据硬依赖 PubChem，当前已设计了三级降级链（PubChem CAS → SMILES/名称 → 类别通用模板 → 通用兜底），确保无 CAS 产品也能生成合规 SDS。

### 2.5 分层架构

后端遵循严格的**View 薄 → Service 厚 → Serializer 纯验证**分层：

| 层 | 职责 | 不允许 |
|----|------|--------|
| **View** | 路由和响应 | 编排多模型工作流 |
| **Service** | 业务逻辑、跨模型写入 | 直接操作 HTTP 请求 |
| **Serializer** | 字段验证、响应塑形 | 业务编排 |
| **Model** | 数据定义 | 业务逻辑 |

**所有 API 响应走信封格式** `{success, data, meta}`，由 EnvelopeRenderer 全局强制。

### 2.6 研究员工作台

研究员（`is_staff=True`）通过 `/workspace/` 工作台管理知识资产和产品：

- **产品编辑页**：完整单元——Word 文档导入 + AI AUTO MATCH 面板 + 知识关联 + COA/SDS 管理
- **工作台仪表盘**：12 项统计指标（产品数、SKU 数、知识实体数等）
- **发布流程**：告知模式而非硬阻断——不完整产品的发布按钮不禁用，只显示警告

**两个管理员角色的明确分离**：
- `IsAdminUser`（superuser）：管理订单/发票/客户——**系统管理员**
- `IsStaffUser`（researcher）：编辑知识/产品维护/发布——**研究员**
- 研究员**不能处理订单**

## 四、后续计划——知识图形的扩展

### 4.1 当前架构的局限

当前的 `ResearchGoal → Application → Method → Protocol → Product → SKU` 链路是**方法论导向**的（"怎么做实验"）。它完美覆盖核苷酸和点击化学，但当产品线扩展到抗体、酶、荧光染料、试剂盒时，会出现结构性缺口：

**当前的模型无法回答"这个试剂在生物体中影响/标记了什么"这类转化导向的高价值问题。**

### 4.2 🟡 P0 待办（扩展前的结构改造）

#### [BIO-P0-1] 引入"生物学语义"维度

加一条平行于方法论链的**生物学链**：
```
Disease / BiologyProcess（疾病/生物过程）
    │ acts_on
Target / Pathway（靶点/通路）
    │
    ▼
（现有）Method → Protocol → Product
```

这样用户就能回答："研究癌症/感染/神经退行时能用哪些试剂"

#### [BIO-P0-2] Product 模型支持生物试剂子类型

当前 Product 偏"小分子化学试剂"（cas / smiles / formula / molecular_weight）。扩展到抗体（克隆号、宿主物种、效价）、酶（活性单位 U/mL）、荧光染料（Ex/Em 波长）、试剂盒时：
- 加 `product_type` 分类（chemical / antibody / enzyme / dye / kit）
- 预留类型化扩展机制（JSON 属性包 / 子模型表）

#### [TECH-P0-3] SDS 解耦 CAS 硬依赖（最紧迫）

当前 `generate_sds()` 硬约束：**无 CAS 直接 raise ValueError**。无 CAS 产品（修饰核苷酸偶联物、酶、混合物等）当前无法生成 SDS。需实现三级降级链：
1. CAS → PubChem（现有高置信路径，保留）
2. SMILES / InChI / 产品名 → PubChem/ChEMBL（中置信，标注偏差风险）
3. category_path → 类别通用 SDS 模板库（低置信，jena category_path 100% 覆盖）

### 4.3 🟢 P1 待办

|----|------|------|

| [TECH-P1-1] | 字段语义去重（Protocol vs ProtocolStep） | 数据一致性 |
| [TECH-P1-2] | 软删除 + 审计追溯 | 数据可恢复、可审计 |
| [TECH-P1-3] | AI 推荐缓存层（Redis） | 生产环境 API 延迟 200-800ms+ |

### 4.5 产品线扩展计划

```
当前阶段（已完成）        → 核苷酸 / 点击化学 / 分子生物学
                        ↓
近期扩展                 → 抗体（克隆号、宿主、验证方式、效价）
```

## 五、演示说明——录屏展示建议

以下是你录屏时可以逐一展示的核心页面和功能，建议按以下顺序组织：

### 第一部分：理念展示（2-3 分钟）

1. **首页**（`/`）：展示平台整体定位
   - Hero 区域的关键信息架构
   - 产品分类 + 知识概览（实体计数）
   - 精选应用/方法/产品展示区
   - 知识图谱预览（Cytoscape.js 渲染的缩略图）

   - 展示产品的**全部知识上下文**——关联应用、关联方法、关联协议、关联文献
   - 这是传统电商完全没有的能力：**一个产品页同时承载科学 + 商业信息**

### 第二部分：研究员工作台（5-8 分钟）

3. **工作台仪表盘**（`/workspace/`）：
   - 12 项统计指标面板
   - 展示研究员视角 vs 访客视角的差异

4. **产品编辑页**——AI AUTO MATCH 核心演示：
   - 打开一个产品的编辑页
   - 在表单中输入 CAS 号（如 `73449-06-6`）
   - 点击 **🤖 AI AUTO MATCH** 按钮
   - **实时展示**：按钮进入 searching 状态 → 返回化学属性预览 + 知识链匹配结果 + 协议推荐列表

6. **知识图谱可视化**（可选）：
