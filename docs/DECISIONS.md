> **为什么只记"为什么"**：
> 「是什么」可以从代码读出来，会随代码更新而自动同步；
> 「为什么」**不在代码里**，一旦丢失就无法恢复。

> 只剩 `docs/PHASE1_TDD_TEST_PLAN.md` 的碎片。**这类信息不可再生。**
>
> ⇒ 所以本文件的核心作用是：**在"为什么"还活着的时候把它存下来。**

### D1 购物车合并时，「叠加超单行上限」选择**跳过该行**，而不是整条拒绝或静默截断

- **背景**：`POST /basket/merge` 提交的是**整个游客购物车**（可能 5-10 行）。若其中 1 行叠加后超 999，需要决定：整单失败？截断？跳过？
- **否决了「整条 400」**：会让**其余 4 件本可成功的商品一起失败**，且前端拿不到部分成功的结果。
- **否决了「静默截断到 999」**：用户会拿到一个"既非请求值、也非原值"的数量，且没有任何提示，更难排查。
- **选择了「跳过 + 明细回传」**：失败面从"整单"收敛到"单行"，并回传 `skipped_items` 让前端能说明白是哪件商品。**代价**：需要新增 `product_name` 字段（`7c2a0f2`）才能让用户知道是哪件。
- ⚠️ **后续发现的重要事实**：我当初支持这个决定的理由是"被跳过的行会留在 localStorage 可重试"——**这个理由不成立**（localStorage 恒 null，见 `CLAIMS.md` C2）。决策本身仍成立，但**它的原始论证有一半是错的**。
- **2026-10-19 / `5463633`、`7c2a0f2`**

### D2 购物车写端点对匿名开放（`AllowAny` + `X-Session-Key` 作用域）

- **背景**：产品要求"游客可以先加购，登录后再合并"。若要求先登录，会损失转化。
- **否决了「必须登录才能加购」**：破坏游客体验，且 P0-2 整个功能（登录后合并购物车）就是为这个场景做的。
- **代价（必须知情）**：匿名用户可写 `basket` 表；隔离仅靠客户端自造的 `session_key`（改 UUID 即新作用域）。**风险与限额见 `CLAIMS.md` C9/C10。**
- **2026 年 6 月设计期（无 git 历史）/ 2026-10-19 复核确认（`AllowAny` 次数 6=6，非新引入）**

### D3 库存累加守卫必须**先查后加**，不可在 `+=` 之后调用

- **背景**：给 `available`/`allocated` 加 int4 上界时，`receipt`/`adjust` 用了"先 `_guard_accumulation(当前值, 增量)` 再 `+=`"，而 `allocate` 写成了"先 `inv.allocate(qty)` 再守卫"。
- **后果**：`inv.allocate()` 内部已执行 `allocated += qty`，守卫拿到的 `current` 是**加完之后的值**，再加一次 `quantity` ⇒ **多算一个 quantity** ⇒ `allocated=INT4_MAX-100` 时 `allocate(60)` 本应成功却被拒（400）。
- **否决了「用 `inv.allocated - quantity` 倒推」**：那是掩盖症状；若 `allocate()` 将来改成直接赋值，倒推立刻又错。
- **选择了「把守卫移到 `inv.allocate()` 之前」**：与 `receipt`/`adjust` 的顺序一致，根因修复。
- **代价**：`available` 不足时会先做一次无用的 `allocated` 检查——无副作用。
- **2026-10-19 / `cac4d79`**

### D4 移除 Ketcher 化学结构编辑器，改为自包含 SMILES 文本输入

- **背景**：`/workspace/products/new` 与 `/:id/edit` 白屏。
- **根因**：`KetcherEditor.vue` 静态 import `ketcher-react`（React 库），浏览器求值阶段引用 Node 全局 `process`（Vite 不 polyfill）⇒ `ReferenceError: process is not defined` ⇒ 异步组件加载失败 ⇒ 整页无法挂载。
- **否决了「加 `process` polyfill」**：只是让 React 库的副作用"看起来不炸"，包体与兼容风险仍在；且引入 React 到 Vue 项目里维护成本高。
- **选择了「自包含 SMILES 文本框」**：功能降级但可靠。
- **代价**：失去图形化结构绘制能力（研究者需手写/粘贴 SMILES）。
- **2026-10（白屏修复）**

### D5 建议给 RFQ 的 `items` 加 `max_length=50`（**待实施**）

- **背景**：`quote-requests` 允许匿名提交，`items` 是 `many=True` 且**无 `max_length`**，子序列化器 4 个字段全部可缺省 ⇒ **`{}` 是合法 item**。实测 `items=[{}]×50000` 通过校验（0.26s），JSON 仅 4 字节/条。配合 `client_max_body_size 20m` ⇒ 单请求理论可塞约 **520 万条**，且写入**逐条 INSERT、无 `transaction.atomic`**，超时被 kill 后已写入的行**不会回滚**。
- **为什么必须做**：这是唯一能把"单请求"变成"数量级放大器"的端点（basket 单请求只能写 1 行）。3 个 gunicorn worker 被 3 个这样的请求占满 = 全站 API 停顿。
- **为什么是 50**：实测正常峰值——单游客 session 最多 4 行、单登录用户最多 6 行、本地 65 个 RFQ **全部只有 1 条明细**。50 ≈ 观测峰值 6 的 8 倍，留足"一次囤一批试剂"的空间，同时把写放大从 520 万压到 50。
- **代价**：若将来出现"批量导入大清单"的真实需求，需同步调大；已存在的记录不受影响。
- **2026-10-19 / 待实施**

### D8 **不做**「购物车合并超限可重试」，也**不删** `pruneMergedLocalItems`

- **背景**：`pruneMergedLocalItems()` 在正常网络下走不到（`localStorage` 为空）。面对这个"疑似死代码"，只有两条直觉路径：改 `auth.js` 让它真正可重试，或删掉它。
- **关键实测（决定了结论）**：
  - ★ 「叠加超 999」在真实数据里**差两个数量级**：`basket` max=**8**、`order_item` max=**9**，≥100 的行数为 **0**（见 `CLAIMS.md` C13）
  - ★ 但 `prune` **并非完全不可达**：`addItem` 的降级条件是 `if (!token)`（`basket.js:99`）—— **匿名 + 加购 API 失败**时会写 localStorage 副本，登录后 `auth.js:58` 的 `filter(_guest || _local)` 能读到它 ⇒ 这条路径上 prune **确实在工作**
- **否决了「改 `auth.js` 让主流程也可重试」**：
  要让正常路径也有本地副本，就必须让成功路径也写 localStorage；一旦有了副本，
  「登出→再登录」就会**二次合并导致数量翻倍**（`basket.js:242-243` 反复警告过）。
  ⚠️ **翻倍是静默的**（用户可能直接下单买多，科研试剂不便宜），而"丢一件"是可见可补救的。
  ⇒ **用可见的小损失换静默的大损失，是负收益。**
- **否决了「删掉 prune」**：它在"匿名 + API 失败"降级路径上有效，删了会引入回归。
- **选择了「保留代码 + 修正描述」**：把 `CLAIMS.md` 里"死代码"的误标改为"仅在降级路径生效"。
- **代价（已知并接受）**：正常网络下，被跳过的商品**仍然会丢**，用户只拿到一条 toast 告知是哪件、为什么、可手动重新加购。
  ⚠️ 但因触发条件（单行 ≥ 999）在现实中几乎不存在，实际暴露面接近 0。
- **2026-10-19 / 仅改文档，代码零改动**
