## 1. 三个基本判断（基于实测，不是感觉）

### 判断一：不是"测得太少"，是"测错了地方"

后端 **2432 个用例 / 57 个模型**，绝对量不算少。但分布是按"写代码的顺序"长的，不是按风险：

| app | 用例数 | 模型 | 用例/模型 | 承载的风险 |
|---|---|---|---|---|
| knowledge | 796 | 10 | 79 | 知识准确性 |
| commerce | 616 | 6 | **102** | 产品/COA/SDS |
| transactions | 386 | 14 | 27 | **钱**（订单/库存流水） |
| bridges | 384 | 9 | 42 | 实体关联 |
| documents | 96 | 5 | 19 | 文档解析 |
| accounts | 56 | 3 | 18 | 身份/权限 |
| **inventory** | **46** | 3 | 15 | **超卖 = 钱** ⚠️ |
| quotes | 31 | 2 | 15 | 报价 |
| assets | 16 | 1 | 16 | 静态资源 |
| **notifications** | **5** | 2 | **2** | **静默失败** ⚠️ |

⇒ TDD 做的知识域上千用例；顺手加的外围近乎裸奔。**但风险不这样分布。**

### 判断二：最大的空白是"并发"，而且本机根本测不出来

```
代码里 select_for_update：17 处
测试里提及 select_for_update：2 个文件
并发/线程相关测试：2 个
```

这 17 处护的是库存和订单 —— **钱**。

更关键：**测试跑在 sqlite 上，`select_for_update` 在 sqlite 下是 no-op**。所以并发问题在本机**测不出来**，现有那 2 个测试还是诚实 skip 的。

⇒ 这一层不是"测得少"，是"**基础设施不支持测**"。

### 判断三：已有资产比想象的多，只是没接线

| 已有 | 实测 |
|---|---|
| e2e spec | **56 个**，4 层 tag（`@readonly` / `@write` / `@prod-ok` / `@local-only`） |
| e2e 执行脚本 | **5 条**：`test:e2e` / `:readonly` / `:write` / `:prod` / `:local`（含 `gate-audit` 审计） |
| e2e 门禁 | `GATE.md` + `gate-audit.cjs`：spec 级定级 + **用例级捞回**（42 例逐条定性、捞回 38） |
| CI | 5 个 job（后端测试 / 变异检测 / 能力映射 / 删除闸门 / 前端构建） |
| 权限断言 | 43 个测试文件含 401/403/permission |

⇒ **发令枪都在，缺的是"把 e2e 接到 CI"这一根线**。

## 2. 测试战略：按风险分配，不按技术分配

### 2.1 风险四问（给每个模块打分）

对每个模型 / 每个页面，回答四问，命中即得分：

| # | 问 | 命中含义 | 分数 |
|---|---|---|---|
| ① | **动钱吗？** 金额、库存、订单、支付、结算、退款 | 错一次就是真金白银 | 3 |
| ② | **管权限吗？** 谁能看/改/删什么 | 错了是数据泄露 | 3 |
| ③ | **不可逆吗？** 删除、发布、审批、结算、外部通知 | 做错无法撤销 | 2 |
| ④ | **会静默失败吗？** 异步任务、通知、缓存、第三方调用 | 用户以为成功、实际没发生 | 2 |

**权重依据 —— 为什么是 3/3/2/2，不是别的**

这是**排序工具**，不是精算公式。权重只反映"错了之后的后果量级"：

| 维度 | 权重 | 依据 |
|---|---|---|
| 动钱 | 3 | 后果是**外部可见的资金损失**，且通常不可挽回 |
| 权限 | 3 | 后果是**数据泄露**，一次就可能构成事故 |
| 不可逆 | 2 | 可通过备份/人工恢复，但有代价 |
| 静默失败 | 2 | 发现晚、排查难，但通常不直接造成损失 |

⚠️ **局限（如实）**：这套权重**没有经过数据验证**，它只是把"该先顾哪个"变成可讨论的形式。
若将来攒到真实故障数据（哪类问题造成过多少损失），应据此重算，而不是继续沿用拍出来的数字。

**总分决定测试强度**（不是"要不要测"，是"测多深"）：

| 总分 | 等级 | 必须做到 |
|---|---|---|
| **≥7** | **P0 资金/权限/不可逆** | L1 单测 + L2 API + **L3 DB 约束** + **L4 并发** + L6 E2E + 变异验证 |
| 4–6 | P1 主流程 | L1 + L2 + L6 冒烟 |
| 1–3 | P2 体验 | L2 权限 + L6 冒烟 |
| 0 | P3 展示 | 只做 L6 冒烟（能打开、不报错） |

**已评定的 P0 清单**（据实测 + `CLAIMS.md` C1–C13）：

```
inventory（库存/allocate/receipt/adjust）      ← ①钱 ②权限 ③不可逆 ④静默 = 10 分
transactions（订单/流水/退款）                  ← ①钱 ③不可逆 = 8 分
commerce（COA/SDS 审批即发布）                  ← ②权限 ③不可逆 = 8 分
quotes（匿名写入无上限，C10）                   ← ②权限 ④静默 = 5→按 P0 处理
accounts（身份/登录/权限矩阵）                   ← ②权限 = 6
notifications（异步通知）                       ← ④静默 = 2→按 P1 处理，但必须"验效果"
```

### 2.2 七层体系总览

| 层 | 名称 | 测什么 | 跑在哪 | 现状 | 有效性证明 |
|---|---|---|---|---|---|
| **L1** | 领域逻辑 | 金额计算、状态机、校验器、匹配算法 | pytest（快） | 有（部分） | 变异测试 |
| **L2** | API / 服务 | DRF 视图、序列化、**权限矩阵**、错误码 | pytest + sqlite | **2432 用例** | 变异测试 4/4 |
| **L3** | 数据层 | 模型、**DB 约束**、迁移 | pytest + `migration_drill` | 16 约束 / 74 迁移 | 正/回填/幂等/反向演练 |
| **L4** | 并发与事务 | 超卖、重复提交、锁顺序 | **需 Postgres** | **17 锁 / 2 测试** ⚠️ | 并发压测（断言最终值） |
| **L5** | 前后端契约 | 字段名/类型一致 | **CI（contract-check job）** | **4 端点 / 158 字段路径**（OpenAPI schema 快照比对；另 3 个端点因 schema 缺 200 定义暂未覆盖） | 快照 + 变异验证 |
| **L6** | E2E | 关键用户路径（真实浏览器） | Playwright + **CI** | **74 spec / 854 例**；CI 只跑 81 例只读（底线闸门） | e2e 变异验证 |
| **L7** | 非功能 | 性能、安全、可访问性 | 混合 | 部分 | 基线对比 |

### 2.3 资源分配的硬规则（"改什么必须测什么"）

⚠️ **先明确一件事：哪些真能拦，哪些只能靠人**（2026-10-20 审计修正）

本表初版写的是「缺了就拦：pre-commit」—— **这是错的**。现有 `.git/hooks/pre-commit` 只做两件事：
`capability_guard`（**删除**能力闸门）+ `mutation_check --changed`（变异检测）。
**它不检查"新增模型有没有配套测试"，也不检查"新增页面有没有冒烟"。**

⇒ **不要写假的拦截。** 写成"必须"但实际拦不住，比不写更糟 —— 它会让人以为有人在看着。

| 你改了什么 | **必须**新增/更新 | 谁来保证 | 真能拦吗 |
|---|---|---|---|
| 新增模型 | L3 约束用例 + L2 权限用例 | **人工 review** | ❌ 拦不住 |
| 改金额/库存/订单逻辑 | L1 单测 + **L4 并发用例** | 人工 + CI（**L4 自 S3 生效**） | ⚠️ 部分 |
| 改权限/可见性 | L2 权限矩阵用例（含 401/403） | 人工 review | ❌ 拦不住 |
| 新增页面 | L6 冒烟（`@readonly` 或 `@local-only`） | 人工 review | ❌ 拦不住 |
| 新增/改 API 字段 | L5 契约检查 + L2 序列化用例 | 人工 review | ❌ 拦不住 |
| 修 bug | **一条 L2 回归用例**（bug 变成测试） | 人工 review | ❌ 拦不住 |
| 改迁移 | `migration_drill --app <app>` 四步演练 | 人工 + CI（可加） | ⚠️ 可加 |
| **删文件/删能力** | `capability_guard --check` | **hook + CI deletion-guard** | ✅ **真拦** |
| **改核心逻辑后测试是否变摆设** | `mutation_check` | **hook（`--changed`）** | ✅ **真拦** |
| **产物/能力映射漂移** | `--verify-map` | **CI** | ✅ **真拦** |

**这张表最重要的一列是「真能拦吗」** —— 它告诉你哪些靠机制、哪些靠制度。
标 ❌ 的条目**必须配人工检查**（PL 或 reviewer 在 PR 里逐条勾），否则它们只是愿望。

⚠️ **L4 相关规则的生效时间**：涉及"改金额/库存必须有并发用例"的条目，
需等 **PostgreSQL 测试环境建成（路线图 S3）** 才具备执行条件。
**在 S3 完成前，这些条目标记为「暂缓」，不参与判定** —— 不要用一条现在还做不到的规则去要求人。

### 2.4 明确不测（省下的力气放到上面）

- 第三方 API 的内部逻辑（只测自己的**适配层**：超时、错误码、重试、降级）
- Django / DRF / Element Plus 框架本身
- 纯展示文案（除非是合规要求，如 RUO 声明、COA 字段）
- UI 像素级还原（只测**可达性 + 可操作性 + 关键状态**）

### 2.5 「测够了没」的量化线

本方案全篇说"必须有"，但"有"到什么程度？**没有数字的"必须"无法执行，也无法拒绝。**

先给一版**临时标准**（后续按实际调整）：

| 等级 | 最低要求 |
|---|---|
| **P0** | 每个写操作端点 ≥ 3 条（匿名 / 普通 / 管理员）；每个金额或库存计算 ≥ 5 条边界；每个 `select_for_update` ≥ 1 条并发用例 |
| **P1** | 每个端点 ≥ 1 条 happy path + 1 条错误路径 |
| **P2** | 每个页面 ≥ 1 条冒烟 |
| **P3** | 不写 |

⚠️ **这些数字是起点，不是真理。** 真正的判断标准是那一句：

> **如果这段代码明天坏了，哪条测试会红？**

红不了，条数再多也没用 —— 这正是 `mutation_check` 存在的理由。
反过来说，**能红的 3 条胜过不能红的 30 条**。

## 3. 分层规范 L1–L7

### L1 领域逻辑（纯函数，无 DB 无网络）

**写在哪**：`backend/apps/<app>/tests/test_<模块>.py`

**必须**
- 每个金额/数量计算函数至少覆盖：正常值、0、负数、上界、上界+1
- 状态机每个迁移边都有用例，且**非法迁移必须报错**（不是静默）
- 校验器：合法/非法/边界三档

**禁止**
- 在 L1 里建 DB 记录（那已经是 L2）
- 用 `assert x` 而不是 `self.assertEqual`（失败信息无法定位）

**有效性证明**：`scripts/mutation_check.py` 对它注入变异（改运算符号、去边界判断），测试必须变红。

---

### L2 API / 服务层（本项目的主力层）

**写在哪**：`backend/apps/<app>/tests/test_api.py` / `test_<场景>.py`

**必须**
- **权限矩阵**：每个写端点至少 3 个用例 —— 匿名 / 普通用户 / 管理员
- 每个端点至少覆盖：200 / 400（参数错） / 403（无权） / 404（不存在）
- 错误响应必须断言**具体错误码或字段名**，不能只断言 `status_code != 200`

**权限矩阵模板**（照抄填写）：

| 端点 | 匿名 | 登录用户 | 员工 | 超管 | 断言位置 |
|---|---|---|---|---|---|
| `POST /api/v1/xxx/` | 401 | 403 | 200 | 200 | `test_api_permission_hardening.py` |

**禁止**
- 只测 happy path
- 用 `raise SkipTest` 逃过"本机测不了"的场景 —— **要么补环境，要么在 CLAIMS 里登记为什么无法测**

---

### L3 数据层（模型 / 约束 / 迁移）

**必须**
- 有业务规则的字段，**优先在 DB 层加约束**（`CheckConstraint` / `UniqueConstraint`），而不是只靠序列化器
- 每条约束配一个用例：**直接绕过 ORM 写非法值，必须被 DB 拦**
- 改迁移必须跑 `scripts/migration_drill.py --app <app>`：正向 / 回填 / 幂等 / 反向

**现状**：16 个约束，19 个相关用例（`inventory/tests/test_int4_overflow.py` 覆盖最好）。

**已知缺口**：74 个迁移里，哪些做过演练**没有记录**。⇒ 建议给每个 app 补一次 `migration_drill` 并记进 CLAIMS。

---

### L4 并发与事务（★ 最大缺口）

**为什么必须单独一层**：本项目 17 处 `select_for_update`，但**测试跑在 sqlite 上，该语句是 no-op**。也就是说：**并发 bug 在本机 100% 测不出来，而线上是 Postgres。**

**必须（新）**
1. 建立 **Postgres 测试环境**（docker compose 已有 pg 服务，只需让测试能连它）
2. 对每个 `select_for_update` 保护的操作，写一条**并发用例**：
   - 起 N 个线程/进程同时执行
   - **断言最终值**（不是断言"没报错"）
   - 例：库存 100，10 个并发各扣 15 ⇒ 最终必须是 100 - 6×15 = 10，且失败 4 个
3. 断言方式：**先查后断言**（读 DB 最终态），不要依赖返回值

**如何证明它有效**：临时把 `select_for_update` 注释掉，并发用例**必须变红**。红不了说明用例无效。

**代价**：需要基础设施改造（测试连 PG）。**这是唯一一个不能靠"多写几个测试"解决的层。**

---

### L5 前后端契约（当前空白）

**问题**：前端和后端各自演进，字段改名/类型变更是**静默失败**的典型 —— 页面不报错，只是显示空白。

**最小可行做法**
1. 导出后端序列化器字段清单（名称 + 类型 + 必填）
2. 与前端消费点比对（可用 `capability_guard --map` 的前端入口数据 + grep 字段名）
3. 不一致 ⇒ 报错

**为什么先做"最小"**：完整 OpenAPI 契约测试成本高；先把"字段名对不上"这个最高频问题拦住即可。

---

### L6 E2E（页面操作，详见 §4）

**必须**
- 只覆盖**关键用户路径**，不做穷举（穷举交给 L2）
- 每条 spec 必须打 tag：`@readonly` / `@write` / `@prod-ok` / `@local-only`
- 遵守 §4 的拟人化七条铁律

**现状**：56 spec / 47 `@local-only` / 9 个可对生产跑（共 67 test）

---

### L7 非功能

| 子项 | 现状 | 最小要求 |
|---|---|---|
| **性能** | 有基线（2 vCPU/3.5GB，gunicorn 3×4） | 改动涉及列表/搜索时，测一次 p95 |
| **安全** | 有匿名写探针（C9–C12） | 每次部署后必跑，且**必须穿透 nginx** |
| **可访问性** | 有 `a11y.spec.cjs` | 新增页面必须过一遍语义化检查（见 §4.10） |

## 4. E2E 编写规范（"怎么测"，不含"测哪些"）

### 4.2 视觉与展示检查清单（每个页面）

| # | 检查 | 怎么验 |

| 1 | 首屏无空白/无闪烁骨架残留 | 截图 + `expect(locator).toBeVisible()` |

### 4.3 拟人化操作七条铁律（**本方案的核心**）

> 这七条是"AI / 自动化能不能替代人"的分界线。违反任何一条，测出来的绿都不算数。

| # | 铁律 | 违反的典型表现 | 正确做法 |
|---|---|---|---|
| **1** | **必须像用户一样操作** | 直接 `page.goto('/workspace/products/new')` 绕过菜单 | 从菜单点进去；表单逐项填；**验证器一步不绕** |
| **2** | **不许绕过页面打接口** | 页面不点，直接 `request.post()` 造状态 | 被测路径必须走 UI；**前置数据**才允许 API |
| **3** | **不许用 JS 塞值** | `page.evaluate("input.value='x'")` | 用 `fill()` / `selectOption()`，让前端验证器跑一遍 |
| **4** | **"成功"提示不算通过** | 看到 toast 就算过 | **列表要刷新、DB 要查到**、状态要变 |
| **5** | **验效果，不看工具返回值** | `click()` 没报错就算点了 | 断言**监听真的触发 / DOM 真的变 / 请求真的发出** |
| **6** | **测试数据必须可识别** | 库里分不清哪些是测试造的 | 自由字段打 `TEST-YYYYMMDD-NNN` |
| **7** | **不赌登录态** | 一路跑到底，中途掉线不自知 | 每条用例前探会话；多页签守先后；冷启动等待写进用例 |

**第 5 条的现实依据**：曾出现 `click success` 但按钮上的一次性监听触发计数为 0 —— 页面正在重渲染，点在了失效节点上，**工具自己不知道**。

### 4.4 定位器策略（为什么这条决定成败）

| 优先级 | 写法 | 说明 |
|---|---|---|
| ✅ 1 | `getByRole('button', { name: '加入购物车' })` | **用户视角**，改版不易挂 |
| ✅ 2 | `getByLabel('用户名')` / `getByPlaceholder` | 表单首选 |
| ✅ 3 | `getByText()`（限定在容器内） | 谨慎使用，易多匹配 |
| ⚠️ 4 | `data-testid` | 可接受，但要保证**长期维护** |
| ❌ 禁止 | `div.list > div:nth-child(1) > button` | **一改版就全灭** |

**实测依据**：同一任务，语义定位比 CSS 链**快 73%**（2.5s vs 5.5s），且页面重构后 CSS 链 timeout、语义定位照过。

### 4.5 等待策略

| ❌ 禁止 | ✅ 替代 |
|---|---|
| `waitForTimeout(3000)` | `expect(locator).toBeVisible()`（Web-first 自动重试） |
| `waitForTimeout` 等接口 | `waitForResponse(url)` 或断言 UI 状态 |
| 固定 sleep 等动画 | `expect(...).toHaveCount()` / `toContainText()` |

**唯一允许 sleep 的场景**：模拟"用户思考停顿"（且 < 500ms，注释写明原因）。

### 4.6 断言策略

**每条断言必须可判定** —— 禁止 `expect(page).toBeTruthy()`、禁止只断言"不报错"。

| 断言对象 | 正确写法 | 举例 |
|---|---|---|
| 元素存在 | `toBeVisible()` / `toBeAttached()` | 不是 `toHaveCount(1)` 了事 |
| 文本内容 | `toContainText('已保存')` | 不断言"页面正常" |
| 数量变化 | `toHaveCount(3)` | 断言**具体数字** |
| 数据落库 | **查 DB**（经 API 或 psql） | 不只信 toast |
| 请求发生 | `waitForResponse` + 断言 body | 不只信 click 成功 |

### 4.7 数据隔离与标记

```
所有测试造的数据，在 name / code / remark / external_ref 等自由字段里写：
    TEST-YYYYMMDD-NNN        （NNN 当日流水，从 001 起）

清理时按前缀删除，一条不漏。
```

**为什么**：数据混杂后清库不敢下手；有标记才能"只删测试数据"。

### 4.8 登录态处理

| 场景 | 做法 |
|---|---|
| 每条用例开始 | **先探会话**（访问一个需登录的接口，401 就重登） |
| 多页签 | 明确先后守则（先登录的页签后操作，或每页签独立 context） |
| 后端冷启动 | 弹窗/守卫的等待**写进用例**，不把"页面没出来"当"未登录" |
| 会话过期（约 40 分钟） | 长流程拆段，或每段前重探 |

### 4.9 弹窗与异步陷阱

| 陷阱 | 规矩 |
|---|---|
| 按 Escape 收日期面板，结果整个业务弹窗被关掉 | **收面板只点按钮，不用 Escape** |
| 列表查询条件跨用例残留 | **每个用例开工先点"重置"** |
| 弹窗卡在 loading，点哪都不动 | 写进已知问题清单，**记录、绕过、提单**，不纠缠 |
| 二次确认弹窗 | 必须显式等待出现，且断言标题文案（防误点同位置的"取消"） |

### 4.10 可访问性（新增页面必过）

- 每个交互元素有可访问名称（`getByRole` 能取到）
- 表单控件有 label

## 8. 测试流程编排（时间轴）

> **§1–§7 是空间轴**（在哪一层测什么），**本章是时间轴**（按什么顺序走、每步怎么交接）。
> 只有空间轴，方案是规范手册；只有时间轴，流程会漏层。

⚠️ **本章的适用性**（2026-10-20 审计标注）

本章来自 15 篇 AI 测试方法论，但**有 3 节当前没有适用对象** ——
本项目 e2e 是**纯 Playwright 固化形态**，没有 AI 驱动测试、也没有 AI 审查器：

| 小节 | 当前状态 | 什么时候才需要 |
|---|---|---|
| 8.4 回放与固化 | **已满足**（e2e 本来就是固化形态） | 若将来引入 AI 生成/执行测试 |
| 8.6 轮次上限 | **暂无对象**（没有 AI 审查器） | 若接入 AI code review |
| 8.7 CLI vs MCP | **仅调试期用**（`playwright-cli` skill 已装） | 若做 AI 驱动的探索式测试 |

⇒ 其余 6 节（**8.1 流水线 / 8.2 先计划 / 8.3 三档标注 / 8.5 多轮合并 / 8.8 两份规矩 / 8.9 速查清单**）**当前就适用**。

**别把"预防性规则"当成"现在就要做"** —— 那会制造无用工作量，也会让真正要做的条目被稀释。

### 8.1 五阶段流水线

```
执行 → 诊断 → 重试 → 合并 → 报告
```

| 阶段 | 做什么 | 触发条件 | 本项目对应 |
|---|---|---|---|
| **1 执行** | 跑指定范围用例 | 总是 | `npm run test:e2e:readonly` / `:local` / `pytest` |
| **2 诊断** | 判断失败是「测试代码问题」还是「产品 bug」 | **有失败才进**（全绿直通报告） | ❌ 无（靠人看） |
| **3 重试** | 只重跑**失败的**用例 | 诊断后仍需验证 | `--grep` 定向 |
| **4 合并** | 把各轮结果合成一份完整数据 | 有重试才需要 | ❌ 无 ⚠️（§8.5） |
| **5 报告** | 出终版结论 | 总是 | Playwright HTML report |

**熔断三条件（任一命中立即停，绝不死循环）**

1. 轮数达上限（默认 2，**硬上限 3**）
2. 本轮**一条都没修好** —— 再跑也是白跑
3. 全部通过

**停机后必须显式列出**：「经 N 轮仍未通过的 X 条用例（清单）」。

⚠️ **熔断不是失败，是分工** —— 它明确告诉你"这几条机器修不好"，剩下的判断本来就属于人。**静默吞掉失败是最坏的实现。**

### 8.2 先计划，再写用例（**最高杠杆的一步**）

**为什么**：一旦对需求的理解错了，后面几十上百条用例全跟着错。计划就是**正式写用例前的评审闸门**。

**流程**

```
需求/页面 → ① 功能清单 → ② 已探索范围 → ③ 差异表 → ④ 测试点 → 【人工确认】 → 用例
```

**①–④ 四块缺一不可**

| 块 | 要看什么 | 典型漏项 |
|---|---|---|
| ① 功能清单 | 有无**多出**本次不测的模块；有无**漏掉**的入口 | 页面上有"批量导入"按钮却没进清单 ⇒ 探索不完整 |
| ② 已探索范围 | 实际走到了哪些页 | 只探到列表页、没进新增/编辑页 ⇒ **先别生成用例** |
| ③ 差异表 | 需求 vs 页面不一致处，**以哪边为准** | 文档没写但页面有的规则 |
| ④ 测试点 | 主流程 / 字段校验 / 异常 / 权限 / 业务规则 | 只列 happy path |

**本项目的落点**：`docs/` 已有 5 份 TEST_PLAN 和 `e2e/GATE.md`，但**没有"PRD → 测试计划"这一层的产物**。建议每做一个新模块，先在 `docs/test-plans/<模块>.md` 落一份计划，review 通过再写 spec。

### 8.3 AI 参与时的三档标注（把事实与猜测分开）

任何 AI 生成的用例/测试点，**每条必须带一个标注**：

| 标注 | 含义 | 评审时 |
|---|---|---|
| **需求依据** | 文档里有原文（附出处） | 直接过 |
| **经验假设** | 按经验补的，文档没写 | 找产品确认 |
| **待确认** | 文档确实没写，我也没依据 | 进评审清单，当面问 |

**现实教训**：某项目 187 条用例里，**155 条的"预期结果"在需求文档里找不到出处** —— 因为分不清哪些是自己加的。加了标注后，评审从 1 小时压到 20 分钟（TL 直接翻"待确认"页）。

**硬规则**：**禁止 AI 自己编业务规则**。没依据就标「待确认」，不要补一个看起来合理的行为。

### 8.4 回放与固化：让 AI 只想一次

**问题**：纯 AI 驱动的测试每次都调模型 ⇒ 登录页一个字没改，也要重新看一遍、想一遍、点一遍 ⇒ 真正的烧钱，且稳定性无法进 CI。

**两种解法（按成本从低到高）**

| 解法 | 做法 | 适用 |
|---|---|---|
| **固化**（本项目现成可用） | AI 只用来**生成脚本**，生成后用普通 Playwright 跑 | 稳定路径（登录、加购、结算） |
| **回放** | agent 首次执行录下动作序列；应用没变就回放，零模型调用；变了才重新推理 | 界面频繁改动的路径 |

**判断标准**：一条路径**每周跑超过 3 次** ⇒ 必须固化，不许每次调模型。

⚠️ 本项目的 e2e 已经是**固化形态**（普通 Playwright spec）—— 这是对的。需要守住的是：**不要让 AI 直接成为 CI 的执行器**（Test Agents 官方也明确"CI 无法直接跑 AI 智能体"）。

### 8.5 多轮合并：为什么"重跑"会把数字吃掉

**这是编排里最隐蔽的坑。**

```
首轮：8 条用例，5 过 3 挂
重试：只跑那 3 条挂的  →  结果文件被覆盖成只剩 3 条
出报告：数字从 8 变 3  ⇒ 全部失真
```

**正确做法**

1. **每轮结果都留档**（`round-1.json` / `round-2.json` …）
2. 出报告前**合并**：以**首轮完整结果**为基底，用各轮重试的最新状态**逐条覆盖**
3. 断言：合并后**用例总数 == 首轮总数**

**本项目的现状**：`package.json` 的 `test:e2e:*` 都是单轮，**没有轮次概念**，所以暂时不踩这个坑；一旦引入自动重试（`retries`），**必须同时实现合并**，否则报告数字会错。

### 8.6 轮次上限与防死循环

**为什么必须有上限**：AI 作者 + AI 审查器互相拉扯时不会自己停。实测有一个 PR 夜里互拉了 **50 多轮**，最后人工叫停。用 `git blame` 分析发现：**被反复揪住的问题里 59% 在第一轮就已经存在** —— 审查器不是在发现新 bug，是在"挤牙膏"。

**四条硬规则**

| # | 规则 |
|---|---|
| 1 | **超过 3 轮 ⇒ 停下，重新思考方案**（不是继续改） |
| 2 | 后续轮次**只审新增的 diff**（别重炒老账） |
| 3 | 指出**整类问题**，要求全局排查（不要一次只改一行） |
| 4 | **禁止重复发布**已经提过的意见 |

**对本项目的意义**：今天 C8 判据改了 4 次（循环论证 → 假设可复现 → 读宿主机 → 边界误报），正是"挤牙膏"的形态。如果早有这条，"第 3 轮就该停下来重新想判据的本质是什么"，而不是继续打补丁。

### 8.7 工具分工：MCP vs CLI（token 账）

| | MCP | CLI |
|---|---|---|
| 交互返回 | **完整可访问性树 + 控制台 + 网络**全进上下文 | 结果**落盘成文件**（快照 YAML / 截图 PNG / Trace），按需读 |
| 实测 | 一次导航 **87000+ token** | 同复杂度**省 4 倍以上** |
| 适用 | **探索 / 调试**（"这一步为什么点不到"） | **长流程回归 / CI / 证据留存** |

**一句话**：**MCP 把东西全倒进上下文，CLI 把东西写进文件。**

**判断标准**：这段交互**要不要反复跑**？要 ⇒ 用 CLI + 落盘；只是看一眼 ⇒ MCP。

**本项目**：`playwright-cli` skill 已安装。跑长流程 e2e 调试时优先用它，把快照落盘后 grep 需要的几行，而不是整棵树塞进对话。

### 8.8 两份「给 AI 看的规矩」：CLAUDE.md 与 REVIEW.md

| 文件 | 谁写 | 回答什么 | 硬要求 |
|---|---|---|---|
| **`CLAUDE.md`** | 团队 | 技术栈、规范、目标与非目标、**可运行的检查命令** | **保持短**（详细内容链出去）；每次审查都加载它 |
| **`REVIEW.md`** | **模块负责人** | **本仓库里"什么叫失败"** | 要具体：`文件:行号` 级证据；限定挑刺数量；**排除不需审查的路径**；无问题时必须明确给"零错误"统计 |

**本项目的现状（实测）**

| 项 | 状态 |
|---|---|
| `CLAUDE.md` | ✅ 有，**220 行 / 13KB**（偏长） |
| `CLAUDE.md` 里的**可运行检查命令** | ❌ **0 条**（grep `pytest/npm run/npx` 无命中） |
| `REVIEW.md` | ❌ **不存在** |

**最便宜的两个改进**

1. 在 `CLAUDE.md` 顶部加一段「可运行检查命令」（照抄 §5.2 与附录 D）
2. 新建 `REVIEW.md`，先写清本项目最容易出的三类失败：
   - 文档/注释说了但代码没做的（如"保留 1 份备份"从未实现）
   - 判据读错了对象（如 C8 读宿主机而非容器）
   - 测试绿但逃过了关键断言（如只断言 `status == 200`）

**附：所有"给 AI 看的文档"都要遵守「位置比措辞重要」**

同一份内容放在不同位置，AI 的注意力完全不同：

| 位置 | 效果 |
|---|---|
| **开头**（「执行前必读」「禁止事项」） | 一定会被重视 |
| **结尾**（「输出格式」「合格线」） | 一定会被重视（收尾强调） |
| **中间** | 容易被扫过去 |

⇒ 所以 `CLAUDE.md`、`REVIEW.md`、测试计划模板、用例生成 prompt，都应遵循：

```
开头：必读清单 + 硬禁止
中间：细节、示例、参考资料
结尾：输出格式 + 合格判定标准
```

**实测依据**：同样的规则集，只把「执行前必读」从中间挪到第一行，遵循率就有明显差别；而把「输出要求」放最后，格式一致性提升最显著。

⚠️ 另一条相关经验：**子指令必须拆文件存**。把"需求拆解/风险识别/边界补充"全塞进一个 prompt，AI 会一口气全吐出来，**分步 workflow 当场失效** —— 因为它看到的是一段连续文本，不是一个有强制顺序的流程。

### 8.9 三条速查清单

**flaky 分诊决策树**（测试偶尔挂，先分诊再改）

```
稳定挂（每次都挂）      → 查断言层：断言对不对、数据准备好了没
多 worker 才挂          → 查数据隔离：是不是共享了登录态/固定账号/同一份数据
随机挂（无规律）        → 查硬等待与竞态：waitForTimeout、动画未结束就断言
只在 CI 挂、本地不挂    → 查环境：时区、字体、视口、代理、并发度
```

**mock 边界矩阵**

| 对象 | 策略 | 本项目例子 |
|---|---|---|
| **第三方服务** | **Always mock** | PubChem / ChEMBL / DeepSeek / Ollama / jena（用 `route.fulfill()` 伪造应答） |
| **自有 API** | **Never mock** | `/api/v1/*` —— 必须打真后端，mock 掉就测不到自己的错 |
| 时间/随机 | 注入固定值 | 订单号时间前缀、`random_state=42` 类 |

**Schema 联动清单**（流水线各段的输出必须能直接喂下一段）

| 上一段输出 | 必须能直接填入 | 若不能 |
|---|---|---|
| 测试计划的「测试点」 | 用例的「测试场景」 | 计划粒度太粗或太细 |
| 用例的「预期结果」 | 断言的「期望值」 | 预期不可判定（写了"正常"） |
| 用例的「前置条件」 | E2E 的数据准备步骤 | 前置没写清 |
| 失败诊断的「推荐复现步骤」 | 重试时定位到具体用例 | 诊断没给可执行信息 |

⚠️ **判断流水线设计对不对，就看这一张表**：上一段输出若需要"人工重新组织"才能喂下一段，说明 Schema 有问题。
