# 部署闸门 · 核心 8 表（CORE8）

> 2026-11-02 立。**这份文档存在的原因**：此前所有部署文档都写「闸门：8 表 Δ0」，
> 但**没有任何地方列出过这 8 张表是哪 8 张，也没有任何脚本可执行** —— 历史上全靠人工数几张。
> 那是一条**真盲区**（"没人知道这里没测"）。本文把它落成具体表名 + 可执行脚本。

## 一、CORE8 是哪 8 张，为什么是它们

判据目的：**重建镜像 / `migrate` / 数据命令不得静默改动既有数据。**

| # | 表 | 归组 | 为什么必须盯 |
|---|---|---|---|
| 1 | `protocol` | 知识实体链 | 协议正文/objective 承载方法证据；量最大（13,895） |
| 2 | `protocol_step` | 知识实体链 | 步骤证据；全库最大表（381,001） |
| 3 | `method` | 知识实体链 | canonical 方法集（83），定义挂在这里 |
| 4 | `application_method` | 知识实体链 | 应用↔方法映射（47,844），一次重算就会整片漂移 |
| 5 | `research_goal` | 知识实体链 | 顶层目标（11,045），上溯链起点 |
| 6 | `method_protocol` | 知识实体链 | 方法↔协议桥（14,975）；桥断了知识链接就断 |
| 7 | `product` | 商业核心 | 前台商品基数；**注意生产 125 条全 `archived=true` 是有意保留** |
| 8 | `sku` | 商业核心 | 价格/库存挂载点（36） |

其余 60 张业务表**照常计数并打印**，但不参与 Δ0 判定（可能因正常业务写入变化）。看到非核心表有 Δ **不等于失败**，但报告里必须解释。

## 二、判据（两条，缺一不可）

1. **行数 Δ0** —— 挡增删
2. **内容摘要一致** —— 挡 UPDATE

> **为什么第 2 条必须有**：行数闸门对 UPDATE 完全瞎。
> 「D 处置」把 443 条 `objective` 置空，行数一个没变 —— 只比行数会**假绿**。
> 摘要用 `sum(hashtext(row::text))`：与行序无关（求和可交换），能捕获任意一行的内容变化。
> 不是密码学哈希，作为"变了没有"的闸门足够，且不必排序整表。

## 三、怎么用

```bash
# ① 部署前抓基线（必须在改动任何东西之前）
python scripts/deploy_table_counts.py \
  --capture work/_deploy_baseline/tables_pre_deploy_YYYYMMDD.json \
  --key "C:/Users/<user>/.ssh/scireagent_deploy_ed25519"

# ② 部署后比对（Δ0 且摘要一致才 exit 0）
python scripts/deploy_table_counts.py \
  --compare work/_deploy_baseline/tables_pre_deploy_YYYYMMDD.json \
  --key "C:/Users/<user>/.ssh/scireagent_deploy_ed25519"

# ③ 判据自检（不连生产，改动脚本后必跑）
python scripts/deploy_table_counts.py --self-test
```

退出码：`0` 绿 / `1` 红 / `2` 环境或基线问题（**2 不等于绿，不许当通过**）。

## 六、这张闸门测不到什么（边界，必须写明）

| 测不到 | 说明 | 补充手段 |
|---|---|---|
| **谁改的、什么时候改的** | 只知"变了"，不知来源 | 查 `AuditLog`，**不要依赖 `updated_at`**（铁律 9） |
| **权限是否被放行** | 与数据无关 | 匿名写探针（见部署清单） |
| **代码是否与产物一致** | 另一个维度 | `check_deploy_consistency.py` 的 C7 / C8 |
| **前端展示是否正确** | 数据对不代表页面对 | e2e / 人工走查 |

⇒ **CORE8 是"数据没被动"的必要条件，不是部署通过的充分条件。**
